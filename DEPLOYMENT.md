# Databricks Apps deployment preparation

These instructions cover the standalone MAP backend and common frontend repositories. MATCH and AUTHOR have their own separate backend repositories and deployment guides.

1. Publish this project folder as its own repository when requested. Keep .env, dependencies, caches, data and large model artifacts out of the repository.
2. Connect the repository source to a Databricks workspace and deploy from this project root. app.yaml contains the start command. Python dependencies are declared in requirements.txt/pyproject.toml; the frontend uses package.json/package-lock.json and builds with npm run build.
3. Configure source, SQL warehouse, model, and artifact access on the **MAP backend app**, not this frontend app. The backend's deployment guide covers the Unity Catalog table resource, SQL warehouse resource, OpenAI secret, writable run storage, and UMAP/FAISS/BGE artifacts. The backend reads the configured Unity Catalog table and exports a run-specific source snapshot for its existing analysis pipeline; it does not require `CAPA_SOURCE_CSV` or `CAPA_SOURCE_SNAPSHOT` in Databricks mode.
4. In the frontend app's **Settings → Resources**, add the deployed MAP backend as a Databricks app resource with **Can use** permission and the resource key `map-api-target`. `app.yaml` exposes that resource as `MAP_API_TARGET`; Databricks supplies the backend app name, and `server.mjs` resolves that name to its URL before proxying requests. An explicit HTTP(S) URL can still be used for local or non-resource deployments. The frontend obtains and refreshes Databricks M2M OAuth tokens using runtime `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID`, and `DATABRICKS_CLIENT_SECRET`; `MAP_API_BEARER_TOKEN` remains an optional server-side override. Do not put credentials in React or browser configuration.
5. Both launchers bind 0.0.0.0 through app.yaml and use DATABRICKS_APP_PORT in Databricks. Verify source and model accessibility, sufficient compute for BGE/UMAP, persistent run storage and the /map/dataset contract in that environment.
6. A fresh MAP backend has no completed run. Start the first small historical analysis with `POST /api/v1/map/runs` and `{"limit": 5}`, then poll its status until it completes. The frontend displays completed analyses but does not start an analysis automatically. Run the backend tests and frontend browser checks again in the deployment environment. Local worker spawning/file locks are suitable for the current single-instance prototype; durable external job execution and shared coordination need to be configured before horizontally scaling it.

Local execution is verified separately; a Databricks deployment has not been performed. This is a deployment starting point, not a claim of cloud validation.

References: [Databricks app deployment](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/deploy), [dependency configuration](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/dependencies), [runtime environment and ports](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/system-env), [app development and source limits](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/app-development).

MAP record annotations are persisted with the run artifacts in CAPA_DATA_DIR/map-runs/<run_id>/record_annotations.json. Provision durable run storage and back it up, including annotation history. Per-record revision checks reject stale updates; these annotations do not approve cluster assignments or write to TrackWise. Validate GET dataset/annotations and PUT annotation requests through the deployed frontend proxy as part of acceptance.
